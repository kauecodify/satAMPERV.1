Visão Geral do Projeto

O satAMPERV.1 é projetado para monitoramento de infraestrutura energética em locais sem conectividade terrestre confiável. O sistema utiliza Wi-Fi/MQTT como link primário de baixo custo e comunicação satelital via modem Swarm M138 como fallback automático.

Implementando o conceito de IoT Governance, os dispositivos não apenas coletam dados, mas participam de decisões distribuídas, emitindo votos assinados com base em condições locais dos sensores.

  • Otimizado para eficiência energética e integridade de dados.
  • Payload em CBOR, reduzindo o tamanho da mensagem em ~28%.
  • Viabilidade comercial com custo operacional minimizado.

const telemetry = {

"dev": "DEV-AM-001",

"ts": 1698765432,

"v": 12.4,

"c": 2.1,

"temp": 28.5,

"vote": 1,

"hmac": "a3f8b9..."

}

// Payload CBOR: ~45 bytes

// Link: Swarm M138 (Fallback)

Características Principais

Arquitetura robusta projetada para ambientes hostis e conectividade intermitente.

Comunicação Híbrida

Wi-Fi/MQTT como link primário. Fallback automático e transparente para satélite Swarm M138 quando o Wi-Fi não está disponível.

Payload Compacto (CBOR)

Serialização binária que reduz o payload em ~28% em relação ao JSON, mantendo a mensagem dentro do limite rigoroso de 160 bytes do Swarm.

Integridade de Dados

Assinatura HMAC-SHA256 em todas as mensagens de telemetria e votos de governança, garantindo autenticidade e não-repúdio.

Memória Otimizada

Uso de buffers estáticos e StaticJsonDocument nas rotas críticas. Nenhuma alocação dinâmica de String no loop principal para evitar fragmentação.

Governança Distribuída

Dispositivos avaliam propostas localmente e emitem votos criptografados, permitindo consenso descentralizado baseado em condições reais do ambiente.

Otimização em Assembly

Filtros de sinal implementados em assembly Xtensa para máximo desempenho e baixa latência na aquisição de dados dos sensores.

Arquitetura do Sistema

Fluxo de dados otimizado da leitura do sensor até o backend na nuvem.

1. Aquisição

Sensores lidos pelo sensor_driver (C) com filtros em Assembly Xtensa.

2. Processamento

CommManager codifica em CBOR, assina com HMAC-SHA256 e decide o link de envio.

3. Transmissão

Wi-Fi/MQTT (primário) ou Swarm M138 via UART (fallback satelital).

Backend valida assinatura HMAC, decodifica CBOR e persiste os dados.

Mecanismo de Governança IoT

O sistema implementa um protocolo leve de consenso distribuído, permitindo que a rede se adapte a condições ambientais locais sem depender exclusivamente de decisões centralizadas.

1

Proposta na Nuvem

O administrador publica uma proposta no tópico governance/proposals.

2

Avaliação Local

Cada ESP32 avalia a proposta localmente com base nos dados dos seus sensores em tempo real.

3

Voto Criptografado

O dispositivo emite um voto assinado com HMAC-SHA256 no tópico governance/votes.

4

Consenso Global

O backend coleta os votos, calcula quórum e limiar de consenso, e aplica a decisão global.

Por que CBOR e não JSON?

  • ~28% menor que o payload JSON equivalente.
  • Codificação binária direta, sem overhead de parsing de texto.
  • Chaves numéricas curtas (1 byte) em vez de strings longas.
  • Telemetria típica em 30 a 50 bytes, com folga dentro do limite de 160 bytes do Swarm.

Custo Operacional do Link Satelital

O Swarm M138 foi escolhido por seu custo por mensagem significativamente inferior ao de concorrentes.

Tecnologia Custo por Mensagem Taxa de Dados Limite de Payload
Swarm M138 (Escolhido) ~ US$ 0,05 ~ 1 kbps 160 bytes
RockBLOCK 9603 US$ 0,04 - US$ 0,14 N/A 340 bytes
Iridium 9603N US$ 0,50 - US$ 1,00 2,4 kbps 340 bytes

💡 Impacto em Escala: Em uma frota de 10.000 dispositivos enviando uma mensagem por dia, a diferença entre Swarm e Iridium pode chegar a milhares de dólares por dia em economia operacional.
